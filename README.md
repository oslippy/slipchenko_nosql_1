# slipchenko-nosql-1

## Теоретичні питання

### 1. Чому аудіо-характеристики винесені в окремий об'єкт `audio_features`, а не зберігаються плоско? Коли таке вкладення вигідне, а коли створює проблеми?

Аудіо-характеристики (`danceability`, `energy`, `loudness`, `speechiness`, `acousticness`, `instrumentalness`, `liveness`, `valence`, `tempo`, `key`, `mode`, `time_signature`) — це логічно пов'язана група полів, які описують один і той самий аспект треку: його акустичні та музичні властивості. Винесення їх у вкладений об'єкт відображає реальну структуру даних і робить документ більш «самоописним»: одразу видно, які поля стосуються метаданих треку, а які — звуку.

**Коли вкладення вигідне:**
- Чітке логічне групування → краща читабельність документа і коду запитів.
- Зручна проєкція: `{ audio_features: 1 }` повертає одразу всі фічі (наприклад, для подачі в ML-модель), без перерахування дванадцяти полів.
- Можна повністю замінити блок одним `$set: { audio_features: {...} }`.
- Простіше додавати нові метрики тієї ж природи — вони лягають у вже існуючий «контейнер».
- Зменшує ймовірність колізій імен з іншими доменами (якщо в схему додадуться, скажімо, lyrics_features).

**Коли вкладення створює проблеми:**
- Шляхи в запитах стають довшими: `audio_features.energy` замість просто `energy` — більше тексту і легше зробити друкарську помилку.
- Індекси на вкладених полях працюють, але кожен індекс треба оголошувати з повним шляхом (`{ "audio_features.tempo": 1 }`); забути префікс — і запит піде по сканах.
- Часткові оновлення окремої фічі вимагають синтаксису з крапкою (`$set: { "audio_features.energy": 0.7 }`), що менш ергономічно.
- Якщо аналітика майже завжди працює лише з одним-двома полями з цієї групи (наприклад, лише з `tempo`), вкладення додає накладні витрати без вигоди — плоска схема була б простішою.
- При експорті в табличні формати (CSV, BI-інструменти) вкладені структури треба «розплющувати» назад.

### 2. Чому виконавці зберігаються як масив, а не як рядок? Які запити стають простішими?

У сирому CSV артисти записані рядком з роздільником `;` (наприклад, `"Daft Punk;Pharrell Williams"`). Це антипатерн для документної БД: у такому полі неможливо нормально шукати, індексувати або агрегувати за окремим артистом — кожен запит вимагатиме регулярних виразів або `$split` під час читання. Масив `artists: ["Daft Punk", "Pharrell Williams"]` відображає реальну кардинальність відношення «трек — артисти» (many-to-many) і робить дані придатними до запитів.

**Які запити стають простішими:**

- Пошук усіх треків конкретного артиста — рівність по елементу масиву працює «з коробки»:
  ```js
  db.tracks.find({ artists: "Daft Punk" })
  ```
- Multikey-індекс на `artists` робить такий пошук ефективним: `db.tracks.createIndex({ artists: 1 })`.
- Пошук треків з кількома конкретними співавторами:
  ```js
  db.tracks.find({ artists: { $all: ["Daft Punk", "Pharrell Williams"] } })
  ```
- Топ-артисти за кількістю треків / середньою популярністю через `$unwind` + `$group`:
  ```js
  db.tracks.aggregate([
    { $unwind: "$artists" },
    { $group: { _id: "$artists", tracks: { $sum: 1 }, avg_pop: { $avg: "$popularity" } } },
    { $sort: { tracks: -1 } }
  ])
  ```
- Фільтр за кількістю співавторів через `$size`: `{ artists: { $size: 1 } }` — лише соло-треки.

З рядком ці запити або неможливі, або вимагають дорогих regex-пошуків без використання індексів.

### 3. Що таке `$out` і чим він відрізняється від `$merge`? Коли використовувати кожен?

Обидва — термінальні стадії агрегації, які записують результат пайплайна в колекцію (а не повертають курсор). Різниця в семантиці запису.

**`$out`** повністю **замінює** цільову колекцію результатом пайплайна. Якщо колекція існувала — її вміст відкидається, індекси (крім `_id`) також. Операція атомарна на рівні перейменування: користувачі не бачать «напівзаписаного» стану. Підходить, коли ціль — повна перебудова деривативної колекції з нуля (класичний batch-ETL).

**`$merge`** робить **інкрементальний upsert**: для кожного документа з пайплайна за ключем `on` шукається відповідний документ у цільовій колекції, і виконується одна з дій згідно з `whenMatched` (`merge`, `replace`, `keepExisting`, `fail`, кастомний pipeline) та `whenNotMatched` (`insert`, `discard`, `fail`). Існуючі документи й індекси зберігаються. Підтримує шардовані колекції та запис в іншу базу.

**Коли який використовувати:**

| Сценарій | Інструмент |
|---|---|
| Перебудувати чисту аналітичну колекцію з сирих даних одним прогоном (як у цьому завданні — `tracks_raw` → `tracks`) | `$out` |
| Щоденне інкрементальне довантаження свіжих документів до існуючої колекції | `$merge` |
| Періодичне оновлення обчислюваних полів (rolling metrics, тижневі агрегати) поверх існуючих рядків | `$merge` |
| Матеріалізований view, який можна спокійно перерахувати з нуля | `$out` |
| Запис у шардовану цільову колекцію (історично — обмеження `$out`) | `$merge` |
| Потрібен strict-mode «помилка при конфлікті» для гарантії унікальності | `$merge` із `whenMatched: "fail"` |

Коротке правило: `$out` — «знеси і поклади заново», `$merge` — «акуратно влий у те, що вже є».
